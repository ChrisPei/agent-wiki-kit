## Core model

Root `AGENTS.md` is neither a copy of the full Wiki nor a place for an Agent to hand-maintain a second content taxonomy. It contains two kinds of resident knowledge:

- L0: human-maintained project direction, decision methods, collaboration model, and Wiki growth contract;
- L1: a semantic index compiled from the real Wiki directory tree and its directory metadata.

L1 must map one-to-one to actual directories. A directory owns knowledge classification, while its `.wiki-meta.json` explains what the directory covers, which high-value conclusions or problems it contains, and when deeper retrieval is useful. `AGENTS.md` stores only the compiled result and must not become a second manually maintained authority.

## Why a second taxonomy fails

If L1 begins with categories invented in the Agent's current reasoning and then points those categories at selected Wiki files, the project acquires two independent maintenance surfaces. The real directory may split, move, or change responsibility while L1 still describes the old categories. New pages also have no unambiguous summary to update. The taxonomy may look semantically rich at first, but it drifts over time.

A directory mirror fixes the maintenance relationship:

```text
real directory
  -> .wiki-meta.json in that directory
  -> build-agent-context
  -> directory guide inside the natural boundaries in AGENTS.md
```

Add or reshape a knowledge category by changing the real directory and its metadata first, then compile it. Do not edit the generated section directly.

## Directory metadata contract

Every directory included in the resident tree uses a `.wiki-meta.json` file:

```json
{
  "title": "Product and Core Experience",
  "summary": "Explains the product, its medium and production strategy, and the highest-value current product decisions and open questions.",
  "order": 10,
  "children": "all"
}
```

- `title`: a non-empty human-readable directory name.
- `summary`: a one-line compression of useful knowledge, not merely “contains product documents.” Include coverage and the most decision-relevant current conclusions, risks, or boundaries.
- `order`: an integer used to order sibling directories. Equal values fall back to path order.
- `children`:
  - `all`: require every direct child directory to have metadata and enter L1; use for semantic category trees.
  - `annotated`: compile only children with metadata; use when a root mixes semantic categories with utility or historical directories.
  - `none`: do not expand children; use for raw assets, generated content, or detail trees that should not consume resident context.

Every compiled directory requires a compiled parent. Prefer `all` for directories that genuinely own knowledge classification so newly added but undocumented categories fail validation. Use `annotated` and `none` only as intentional context pruning, never to conceal missing summaries.

When a directory summary mentions candidate numbers, temporary categories, or unvalidated architecture, compress its maturity as well as its conclusion. L1 residency amplifies apparent authority. A repository-wide candidate remains a candidate, and three named responsibilities do not automatically imply three implementation modules.

## Generated directory-guide contract

The generated guide uses a normal level-two heading as its start and a Markdown separator as its end instead of exposing mechanical start and end comments:

```markdown
## Agent Wiki Directory Guide

> This section is generated by Agent Wiki Kit from directory metadata. Edit `.wiki-meta.json` and rebuild instead of editing the directory list below.

...compiled directory tree...

---
```

The compiler may only:

1. append the complete guide when the configured heading does not exist;
2. when the heading exists exactly once, find the first standalone `---` after it and replace the entire bounded section;
3. preserve human-authored instructions before and after the boundaries byte-for-byte without reordering, formatting, or rewriting them;
4. fail rather than guess when the heading is duplicated or the closing separator is missing;
5. usually place the guide last, while preserving content accidentally appended after the guide on the next build;
6. recognize legacy `<!-- agent-wiki:l1:start/end -->` markers and migrate them once on the next build;
7. compare without writing when `--check` is present.

Run:

```powershell
node <skill-path>/scripts/wiki-kit.mjs build-agent-context --root D:\TargetProject
node <skill-path>/scripts/wiki-kit.mjs build-agent-context --root D:\TargetProject --check
```

Strict `check` also reports a missing generated section, invalid metadata, or stale compiled output.

## Reviewing directory summaries after document changes

The helper cannot decide whether new content changes a directory summary. It stores content fingerprints for documents that an Agent has semantically reviewed:

1. a Wiki document is added, removed, or changed;
2. `check` lists the changed direct documents for each affected directory;
3. the Agent uses `list-topics` to read fixed-header summaries and decides whether the directory's `.wiki-meta.json` summary must change;
4. after making or explicitly declining that semantic change, the Agent runs `review-directory`;
5. the tool records current fingerprints and stays quiet until those documents change again.

```powershell
node <skill-path>/scripts/wiki-kit.mjs review-directory --root D:\TargetProject --path llm-wiki/wiki/product
```

Use `reviewFiles` in `.wiki-meta.json` to restrict direct documents; the default is `["*.md"]`. An empty array disables summary-review reminders for that directory and is useful for immutable raw material or pure archive detail. The command maintains `reviewedDocuments` and `lastReviewed`; do not hand-edit them. Fingerprints are more reliable than one date because a document may change multiple times in a day, but they still detect change rather than understand meaning.

## Fixed headers, summary listing, and the document graph

Every maintained topic provides fixed fields between its H1 and first H2: `status`, `owner`, `last_updated`, `confidence`, a one-line `summary`, `source_refs`, `related_pages`, and `standalone`. `list-topics` reads only those fields so an Agent can judge relevance without loading full bodies.

`check` combines Markdown links and `related_pages` into a document graph, then warns about topics unreachable from the index or with no inbound or outbound edge. If isolation is intentional, run:

```powershell
node <skill-path>/scripts/wiki-kit.mjs mark-standalone --root D:\TargetProject --path llm-wiki/wiki/example.md
```

The command only sets the header field `standalone` to `true`. It does not rename files, delete relationships, or decide on the Agent's behalf whether isolation is justified.

## Adapting the model to a project

Do not choose L1 categories from a fixed template. Audit:

1. the project's most common tasks and most expensive mistakes;
2. which knowledge must reside in L0 to change decisions before category selection;
3. which retrieval questions have stabilized into real directories;
4. which directories are only sources, logs, archives, or generated detail and should be compressed or pruned;
5. whether a new Agent can tell what roughly exists and where to go deeper from only L0 and the compiled tree.

A minimal recovery skeleton often includes current state, a log, sources, and plans. Product, story, operations, research, security, incident, and other categories remain project decisions. A template may supply metadata and compilation mechanics; it must not invent the project's taxonomy.

## Examples are not special rules

A concrete example from a user or creator is often a probe into an underlying mechanism. Reason through:

```text
example -> why it was chosen -> general mechanism -> peer directories or objects -> boundaries and counterexamples -> current change
```

For example, Postmortem may be an important directory in one project, but that does not mean only Postmortem should expose key lessons in L1. The general rule is that every compiled directory must provide enough semantic summary to establish a rough mental model before deeper retrieval.

## Acceptance criteria

- Every node in the generated tree maps to a real directory and metadata file in that directory.
- Removing or moving a directory fails or changes the build instead of leaving a ghost category.
- Changing one directory summary makes `--check` report stale output, while a real build changes only the bounded directory guide.
- Human instructions before and after the guide remain byte-for-byte identical across builds.
- A new Agent can restate each directory's coverage, key conclusions, and deeper entry points without reading the detailed index.
- The same Agent can select a small set of directories for a real task instead of loading the whole Wiki.
